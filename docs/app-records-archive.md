# Automatic app_records archive

The Vercel cron calls `/api/internal/app-records/archive` every five minutes.
Each invocation processes at most one batch of the 50 oldest rows, ordered by
`created_at`, `namespace`, `record_key`. Fewer than 50 rows are left untouched.
All namespaces are included, including device profiles and installation auth.
Deleting these records can invalidate device authentication and remove history.

## Deployment configuration

Set `DATABASE_URL`, `PERSISTENCE_BACKEND=postgres`, `CRON_SECRET`, and the existing
R2 credentials (`CLOUDFLARE_R2_ACCOUNT_ID`, `CLOUDFLARE_R2_ACCESS_KEY_ID`,
`CLOUDFLARE_R2_SECRET_ACCESS_KEY`, `CLOUDFLARE_R2_BUCKET`). Set
`APP_RECORDS_ARCHIVE_R2_BUCKET` to a dedicated **private** archive bucket accessible
with those credentials. Do not expose it through a public R2 domain or the audio
delivery Worker: archives can contain installation secrets' hashes and conversations.
The archive bucket is intentionally explicit rather than defaulting to the audio bucket.

Deploy this code to activate the schedule. The hosting plan must support a
five-minute cron. On other hosts, configure a scheduler to GET the same endpoint
with `Authorization: Bearer <CRON_SECRET>` every five minutes. Authentication is
required in development as well as production. Missing configuration fails closed.
Neon quota errors must be resolved before any export can run.

## Files and recovery

Objects are stored at `archives/app_records/YYYY-MM-DD/<batch UUID>.json`.
JSON contains `export_version`, `batch_id`, `exported_at`, `source_table`,
`record_count`, and `records` (all eight columns, including the complete `value`).
JSON is generated by PostgreSQL and transferred as UTF-8 bytes, preserving numeric
precision and timestamp precision. Audio URLs are references, not audio backups.

The durable `app_records_archive_job` singleton stores the snapshot and destination
until completion. A ten-minute lease prevents overlapping runs from processing the
same job. Failed runs reuse the original snapshot and object key. A crash requires
waiting for the lease to expire; a caught error releases the lease immediately.
Upload uses a conditional write and never overwrites an existing object. The full
object is downloaded and compared byte-for-byte before deletion is attempted.

Deletion and job completion are one atomic SQL statement. Ownership, row contents,
and PostgreSQL row version must still match. Updated/replaced rows remain in the
database for a later batch; therefore `deleted` can be less than 50. The archive
still contains the 50 original snapshots. Completed files are never cleaned up by
this task. Logs contain the object key, checksum, exported and deleted counts.
If a retry finds a different object at the same key, it fails without deleting rows;
investigate that object and pending job before resuming.

This change does not add Telegram delivery, a restore UI, or deploy credentials.
